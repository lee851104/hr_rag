# Design

## Context

本案是獨立新專案，使用者已確認現有 `rag-chatbot-main` 僅供參考。階段 0 的 0.1–0.6 已完成（環境鎖定、共用型別、模型介面、短樣本實測、最小稽核與預算檢核，見 reports/stage-0.md）；2026-10-18 規劃審查後新增真實長度可行性實測；第一次實測用本機 Qwen2.5-1.5B 生成，正確 0/5 未達標（reports/runtime.md）。使用者同日決定生成改用 OpenAI API，embedding 與重排維持本機，並由 Codex 執行後續實作；階段 0 因此改為 0.7 實作 OpenAI 生成、0.8 重跑實測、0.9 定案，完成前不進入階段 1。正式語料、評估題、檢索與網頁仍未建立。動機與範圍見 proposal.md；可驗收行為見五份 specs/*/spec.md。

## Goals / Non-Goals

**Goals:** 以可學習、可測試的小型 Python 系統展示三項能力：引用官方依據、區分公司流程、檢索前權限控管。先證明資料與檢索，再接生成與展示頁。

**Non-Goals:** 不將本機 Demo 宣稱為生產級服務；不將「零次測試洩漏」宣稱為形式化安全保證。其餘排除項沿用 proposal.md。硬性驗收門檻是本專案的目標，不是業界標準或預測成果。

## Decisions

### 1. 最小技術組合

建議 Python 3.12、venv、pytest、SQLite、NumPy、sentence-transformers、jieba、rank-bm25、FastAPI、Jinja2 與一般 HTML/CSS。鎖定實際安裝依賴版本；文件 UTF-8，程式依 PEP 8。階段 0 已以 hash 鎖檔安裝並驗證上述套件；OpenAI 生成需要的官方 openai SDK 與 tiktoken 於 0.7 補鎖；網頁執行另需的 uvicorn、python-multipart 尚未入鎖，於階段 3 補鎖，繁簡檢查用的字表依賴於階段 5 補鎖。重新解析鎖檔時須保留 Torch 官方 Windows wheel 的單一 SHA256，並在全新 venv 以 --require-hashes 安裝及 pip check 驗證。

SQLite 保存文件、版本、片段與稽核；NumPy 保存與計算小型向量矩陣。10 份文件先使用精確向量比對，便於先取得授權 ID 子集合再評分。未選獨立向量資料庫，因本版不需要分散式索引；未選 SPA，因展示頁不需要額外前端建置。保留向量儲存介面，未來擴充須另開變更。

生成器使用可替換介面。2026-10-18 起正式生成改用 OpenAI API（使用者決定，見下方「外部生成」）；embedding（bge-small-zh-v1.5）與重排（bge-reranker-base）仍在本機。階段 0 的本機 llama.cpp／Qwen2.5-1.5B 只保留為 0.4 煙霧測試與第一次實測的紀錄，不作為驗收生成器，也不再是安裝必要條件。先用測試替身完成非模型功能，替身結果不能算生成驗收。

0.1–0.6 的短樣本（每筆約 210 輸入 tokens、單段虛構證據）只證明介面可運作，不代表正式負載。階段 0.8 以公開法條與主管機關問答組成接近正式上限的上下文（約 1,500–2,000 證據 tokens、3–5 個完整父段且含至少 1 個雜訊段），用 5 題可行性樣本量測關鍵主張與引用正確性、繁體輸出、本機檢索與 API 往返耗時、本機 encoder 記憶體，以及每題 token 用量與成本。可行性門檻為 5 題至少 4 題關鍵主張與引用正確、全部為繁體輸出、單題總耗時皆低於單次逾時。這 5 題是可調整的可行性樣本，不得改寫成 30 題評估集或保留題。第一次實測（本機 1.5B，正確 0/5）的紀錄保留在 reports/runtime.md 與 feasibility-long-context.json，0.8 另存結果，不覆寫。

0.8 的模型選擇：從 OpenAI 當時官方模型清單中挑選支援 Structured Outputs（嚴格 JSON schema）的模型，至少比較一個小型低價模型與一個較大的模型，使用同一組 5 題與上下文；在達到可行性門檻的模型中選每題成本較低者，以帶日期的快照模型 ID 鎖定。候選模型、官方價格與查證日期記錄在 reports/runtime.md，價格以 OpenAI 官方定價頁為準，不憑記憶填寫。全部候選都未達標時停止，請使用者決定（更大的模型、調整提示或降低門檻）。降低驗收門檻或縮減範圍屬需求變更，由使用者決定並先更新規格。0.9 記錄最後選擇、預算、逾時與成本上限，並凍結到 config/models.lock.json、settings 與 reports/runtime.md。

**外部生成（OpenAI API）**

2026-10-18 使用者要求自動載入 `.env`：固定以程式位置定位專案根目錄，不搜尋目前工作目錄或上層其他專案。每次生成前只讀 `OPENAI_API_KEY`、`HR_RAG_COST_LIMIT_USD`，既有環境變數優先（含明確空值）；不寫回檔案、不變更全域環境、不快取憑證。支援單行值、成對引號、註解及UTF-8 BOM，不執行shell或變數展開；檔案缺失回退環境設定，讀取／格式錯誤回傳固定not_configured。`.env` 不得自動啟用真實測試或改變API端點。測試以暫存假設定隔離，不能讀取使用者的 `.env`。

- 呼叫方式：使用官方 openai Python SDK（版本 hash 鎖定），以 Structured Outputs 的嚴格 JSON schema 回傳 Answer（status、claims、citations、reason）。伺服器仍以 pydantic 重新驗證，並做引用白名單與繁簡檢查；API 支援時設定不在 OpenAI 端保存回應（例如 Responses API 的 store=false）。
- 端點與金鑰：只允許 https://api.openai.com/v1，不接受任意 base_url。金鑰由使用者自行建立，只從環境變數 OPENAI_API_KEY 或不入版控的 .env 讀取；.env.example 只放空白欄位。金鑰與 Authorization header 不寫入日誌、稽核、報告或例外訊息；缺金鑰時回傳受控錯誤。
- 送出的資料：只有系統提示、使用者原始問題與本次最終上下文單位（摘要模式為id與正文；原文候選另含同一授權單位的document_id、version_id、section_id），不送 user_id、帳號、角色名稱或 session。上下文已先經權限與日期過濾，所以虛構限閱文件 C03、C04 只在該角色有權時才會送出。第一版不處理真實個資，介面提醒使用者不要輸入個人資料。README 寫明資料會送到 OpenAI，附 OpenAI API 資料使用政策連結與查證日期，不自行宣稱對方的保存或訓練政策。
- 參數：模型支援時 temperature=0；不支援時（例如推理型模型）記錄未套用，把推理 tokens 算進輸出預算，推理強度設為最低可用值。max_output_tokens 由 0.9 凍結。
- token 計算：呼叫前以所選模型對應的 tiktoken 編碼計算完整輸入並做預算檢查；呼叫後以 API 回傳的 usage 核對並記錄差異；估算比實際少超過 5% 時調高 safety_margin。context_limit 是本專案自訂的成本與延遲上限，不是模型的上下文上限。
- 逾時與重試：單次逾時與重試次數由 0.9 凍結，初始建議 60 秒、遇 429 或 5xx 最多重試 2 次並指數退避；仍失敗時回傳受控錯誤（timeout、rate_limited、unavailable），不回傳捏造答案。
- 成本控制：每次呼叫記錄 response id、實際模型 ID、輸入與輸出（含推理）tokens，以及依官方價格估算的成本。環境變數 HR_RAG_COST_LIMIT_USD 設累計上限，達上限即停止呼叫並回傳受控錯誤 cost_limit；使用者另在 OpenAI 後台設定用量上限。粗估全專案約 300–600 次生成呼叫（開發題反覆調整、穩定性 18 次、驗收 38 次與重跑），輸入約 0.6–1.2M tokens；實際費用以 0.8 量測和官方價格換算。
- 測試：預設 pytest 只用假 client，不連網、不需金鑰；真實 API 測試必須明確設定 HR_RAG_LIVE_API=1 才執行，並計入成本紀錄。

0.9凍結補記（2026-10-18，接續Decisions 1）：使用者收到0.8比較後指示繼續，正式生成預設為gpt-4.1-mini-2025-04-14；context/evidence/output/safety為4096/2048/512/128，API逾時60秒、重試2次、P95告警45秒、encoder常駐及2 threads，成本建議1美元。完整證據與理由見reports/runtime.md及config/models.lock.json。必要時使用者允許評估Luna為較大候選，但未實測、不自動fallback，仍受相同可行性門檻與原累計成本上限限制。兩個0.8候選2027-01-14停用的限制保留，正式切換前須另行查證及驗證。

### 3. 日期及索引發布

版本欄位：document_id、version_id、title、source_type、source_url、is_synthetic、published_at、revised_at、effective_from、effective_to、fetched_at、date_evidence、allowed_roles、content_sha256、review_status、raw_path、normalized_path。日期使用 ISO 8601；業務日期依 Asia/Taipei。來源使用民國紀年時（全國法規資料庫的「修正日期：民國 113 年 07 月 31 日」及條文中的「一百零六年一月一日」），以民國年加 1911 轉為西元並驗證日期合法，原始字串保存在 date_evidence；轉換規則有單元測試，不合法或無法解析者進入待核對。公開網址缺乏有效期時，人工查證適用法規與沿革並寫 date_evidence；無法查證就不發布到有效索引。

主管機關問答（O05、O06）屬解釋性資料，頁面沒有生效日：effective_from 採頁面項目的發布日期，date_evidence 註明「依問答發布日期，非法規生效日」；頁面項目的更新日期只在人工比對確認內容有變動時記為 revised_at，否則只寫入 date_evidence；網站頁尾的民國更新日不是任何文件日期。查詢日期早於問答發布日時，該問答不提供證據，只能依當時有效的法規回答或回覆資料不足。

主文件另記 source_publisher、maintenance_owner、last_reviewed_at、next_review_due。maintenance_owner 是本專案維護責任，不是新增登入角色；官方資料由專案資料維護者核對，模擬制度由專案制度維護者核對，同一人可兼任。初始核對週期 30 天，可在清單明示調整；到期只產生待核對項，不把網站擷取成功當成人工內容核對完成。

法規可能分條文施行：片段可具更細的有效區間，不能一律繼承整部法規最後修正日。全國法規資料庫的條文沒有施行日欄位，分條施行日寫在施行條款內文（例如勞動基準法第 86 條）；只對納入索引的條文逐條依施行條款及法規沿革頁人工核對，記錄於條文層 effective_from 與 date_evidence。文件頁「網站更新日」不是文件修正日。相同 document_id 的版本有效區間不得重疊；歷史查詢只在已收錄且有查證的區間內承諾。

將清理後文字、段落定位與 hash 對應原始快照；以條文／完整問答建立父片段，再分子片段。子片段會送進 embedding 與重排器，兩者上限都是 512 tokens（中文約一字一 token，含特殊符號）；重排時查詢與片段共用這 512 tokens。因此子片段硬上限為 400 個 encoder tokens（以實際 tokenizer 計數，不以字數估算），初始目標 200–400 中文字；同義詞擴展後的查詢表示上限 96 個 encoder tokens，超過時回傳受控錯誤而不截斷。超過片段上限時依項、款、段落拆分，父片段負責保證條件與例外的完整；單一句子仍超限時標記待人工處理，不得截斷或略過。上限內的長度與 overlap 只用開發集調整，不預設切片數為驗收門檻。

建立新索引 generation 到 staging，完成全部檢核後切換 active generation。失敗保持前一版；文件撤回、角色變更與索引世代變更都要重新取得 eligible IDs，不沿用答案快取。舊版本仍保留供日期查詢，已撤回版本不得對一般使用者提供。

增量向量重用鍵由片段正規化文字 hash、embedding 模型 revision 與相關前處理設定組成。對未變內容保留穩定片段 ID；只增補新增／文字改變片段的向量，刪除的片段同步退出向量與 BM25 路徑。小型 BM25 可重建，但不能因此對所有文件重算 embedding。ACL／有效日期變更更新中繼資料並重新驗證發布，不觸發 embedding；模型或切片設定改變才允許具明確原因的全量重建。

### 4. 查詢流程與授權

登入驗證 → 建立伺服器 Principal → 解析／檢查日期 → 中文查詢前處理 → SQLite 選出 eligible chunk IDs → 在此集合內執行檢索 → 可選重排 → 授權父段落展開／去重／排序／相關度篩選／預算檢查 → 生成（OpenAI API，只送問題與最終上下文）→ 引用與繁體輸出驗證 → 回答與受限稽核。檢索、權限與稽核都在本機完成，外部 API 只負責生成。

日期解析範圍：第一版只辨識問題中明確的絕對日期，包括西元（2026-10-01、2026年10月1日）與民國（民國115年10月1日、115年10月1日）；與查詢日期（欄位值，未填時為 Asia/Taipei 當日）不同時要求釐清，回覆同時顯示兩者。只到年或年月的日期，查詢日期不在該期間內時同樣要求釐清。「今年」「明年」「上個月」等相對說法依查詢日期解讀，不判為衝突，也不自動推算成另一個查詢日期；需要其他時點時請使用者填寫日期欄位。

三個本機示範帳號的角色由伺服器設定，密碼雜湊保存；登入設定 HttpOnly/SameSite cookie，變更操作具 CSRF 防護，預設只監聽 127.0.0.1。沒有開放註冊、任意 role 切換端點或匿名 HR 帳號。限閱只是模擬公司設定，不能把它描述成真實企業機密。

向量與 BM25 路徑都只能回傳 eligible IDs。重排器輸入與父片段展開再斷言授權／時間有效。引用查閱重新驗權；一般查詢紀錄僅限本人。本機開發者可讀受限稽核檔，不向三個 Demo 角色開放全域 debug 頁。

本人歷史紀錄也不是永久存取許可：每次讀取依目前角色、來源撤回狀態及原查詢日期重新驗證，若依據已不可存取則隱藏相關主張與原文；無法安全拆分時隱藏整份答案。回饋只顯示分類與狀態，不複製答案正文來繞過撤回。

### 5. 檢索與生成實驗

A：純向量 top-5。B：向量與 BM25 各取至多 20 個合格候選，以 RRF 合併（常數 60），取 top-5。C：B 合併後至多 20 個候選經重排，取 top-5。不足數量直接使用全部合格結果；固定 chunk_id 為同分排序依據。中文斷詞保留條號、日數與原文專有名詞。

查詢前處理使用小型人工同義詞設定，初始至少含「特休／特別休假」，不導入另一本知識文件或複雜 NLP。保留原始問題，建立共用的正規化與同義詞擴展表示供 dense、BM25、reranker 使用，生成仍收到原始問題。詞表不可把「補休」視為「特休」，不可刪除否定、數值或日期；版本與 hash 隨實驗凍結。配對控制題與反例屬工程測試 fixture，不增加 30 題獨立評估集；開發報告另列開關前處理的差異。

僅在開發集選最終模式；比較結果不要求 C 必定勝過 A。固定模型、資料快照、切片、提示、日期、角色與 Top-K 後才比較。top-5 指父段落展開前的最終檢索片段，不能靠展開全文偷偷改善命中計分。

上下文組裝先依 document_id/version_id/parent_id 合併重複父段。跨來源完全相同正文只在來源類型、有效區間與適用範圍一致時合併，保留全部合法來源映射；不同官方／公司內容、條件或衝突不可用相似度刪掉。排序依最佳子片段名次，再依來源類型與穩定 ID 同分排序；來源類型只是展示次序，不是解決法規衝突的判定器。

去重排序後、預算檢查前，以相關度篩選決定送入模型的單位：參數為 context_max_units（1–5）與 min_relevance。模式 C 使用重排分數門檻；模式 A／B 使用該模式最終分數相對第一名的比例門檻；至少保留排名第一的單位。兩個參數只用開發集調整並隨實驗凍結、寫入 config_hash，被篩掉的單位記入 dropped_reasons。篩選讓檢索召回（Top-5 計分）與送入模型的上下文分開：Top-5 命中仍在篩選前計算；組裝後全組命中與上下文精確度在篩選後計算，所以過度篩選會由組裝後命中門檻抓出，不能用篩選換取精確度。

階段 0 記錄模型上下文上限、token 計算方式、output_reserve、safety_margin 及 evidence_budget；完整提示、問題、證據、輸出保留額度與安全餘量總和必須在上限內。0.6 的預設值（本機上限 4,096、evidence_budget 2,048、output_reserve 512、safety_margin 128）原是本機 Qwen 的短樣本設定。第一次實測：勞基法第 38 條約 440 字，5 個完整父段以 Qwen tokenizer 計為 1,715 tokens，在 2,048 內，預算不是瓶頸；但有一題輸出達 512 上限。改用 OpenAI 後 token 計算改為 tiktoken 估算加 API usage 核對（見 Decisions 1），context_limit、evidence_budget、output_reserve（推理型模型須含推理 tokens）與 safety_margin 由 0.9 依 0.8 結果重新凍結；改值後 0.6 的超限與負值測試要重跑。證據以完整條文／問答為預算單位，按固定次序納入，過大單位整個略過並記原因，不能截斷例外；若提示與問題本身已超限，生成前回傳受控錯誤。引用白名單由最終實際輸入上下文建立，不是原始候選集合。金標證據組只供評估，不在執行期用答案補足上下文。

生成回傳結構化 claims 與 citation IDs，再由伺服器對本次 evidence 白名單驗證，無效引用直接失敗。生成模型可能輸出簡體字（第一次本機實測就出現），所以伺服器以鎖定版本的繁簡字表檢查主張與原因文字；出現簡體專用字時視為輸出格式錯誤，回傳受控失敗並計入錯誤率，不自動轉換後當成通過（若要加入自動轉換，須先更新規格並記錄轉換次數）；語義支持由人工評估確認，不能聲稱 ID 驗證已能保證內容正確。資料不足以 evidence 判斷與生成判斷共同處理，相似度分數不是通用可信度。對衝突標示待核對；必要時只提供可確認部分。

### 6. 評估與計分

30 題分為直接查詢 10、改寫／跨文件 8、日期版本 4、權限 4、資料不足 4。開發／保留分配依序 6/4、5/3、3/1、3/1、3/1，即 20／10 題。先由人工完成答案及證據核對再調參；LLM 可以協助草擬，但不能自行當裁判定稿。

每題記錄 question_id、category、split、question、as_of、role_expectations、author、reviewer、reviewed_at。role_expectations 以角色為鍵，每個角色各有 expected_behavior、answer_key、required_evidence_groups、forbidden_sources；權限題必須三個角色都填（例如 employee 為資料不足或只答官方部分、hr 為完整回答），其他題只列實際執行的一個角色。每次執行依該角色的預期計分。證據採 document_id+version_id+section_id；每個 required group 內允許等價段落，跨文件需要的多組則全部必要。評估檔不在 ingestion allowlist 中。

總可回答題為 22；Top-5 完整證據命中至少 20/22，答案完整正確至少 20/22；保留題中可回答的 8 題，兩項均至少 7/8。題目所有關鍵答案與限制條件皆正確才給 1，否則 0。4 道版本題、4 道資料不足題各 4/4。權限 4 題各跑三角色為 12 次；因此單模式一次完整驗收為 38 次提問，不把它寫成 38 道獨立題。

引用支持率至少 95%，關鍵主張引用覆蓋率 100%；語義正確由人工核對。所有無權片段、錯誤時間片段及權限側路測試失敗次數必須為 0。一般失敗不得從分母刪掉；模型錯誤列入失敗與錯誤率。

保留既有 Top-5 全組命中門檻，另報必要證據組覆蓋率（已覆蓋必要組／全部必要組，逐題平均），分別量測最終 Top-5 與組裝後上下文。組裝後全組命中也須開發至少 13/14，最終至少 20/22 且保留至少 7/8，避免檢索已命中但預算移除關鍵證據。

Context Precision 以人工標註的「有助回答的去重上下文單位／全部去重上下文單位」計算，再對可回答題取逐題平均；單位為送入模型的完整父條文／問答，合併來源不能重複計數。必要依據、限制及例外均算有用，純粹同主題但無助回答算雜訊；人工另記混合段落的雜訊，不能藉合併任意長段落改善分數。開發 14 題與保留 8 題的平均精確度分別至少 80%；空上下文／執行錯誤記 0 並列原因。80% 是本案新增驗收目標，不是簡報宣稱的標準或已測成績。三模式皆報告，最終選定模式須達標。

有用性標註以 (question_id, role, 單位內容 SHA256) 為鍵存成標註檔，並以 hash 凍結；同一單位在不同模式或重跑時直接重用，只有新出現的單位需要人工標註；修改既有標註須記錄原因與標註者。保留題的標註由使用者完成，存放位置與保留題相同。

在階段 1 預選 6 個開發案例（官方、公司、跨文件、版本、權限、資料不足各一），各固定角色、日期與預期結果。階段 5 以真實模型各獨立執行三次，總計 18 次，核對關鍵主張、狀態、引用、版本與授權皆正確且無矛盾；措辭可不同。可用時固定 seed 並採低溫度，記錄供應商不支援的設定，不保證模型位元級確定性。這 18 次為額外穩定性執行，獨立題仍為 30 題；凍結設定改變須重跑。

只用開發集作模式與提示選擇；保留集由使用者／驗收者持有，實作端不讀答案調參。公司文件 C01–C04 與開發題可由 LLM 草擬再人工核對；10 題保留題（題目、各角色預期與證據組）由不參與實作調參的一方草擬，使用者審核定稿：2026-10-18 由 Claude 草擬（此後不參與調參），使用者核對；不得交給 Codex 或任何參與調參的 agent 草擬、修改或讀取。author 欄位照實記錄草擬者，reviewer 記錄使用者。H07–H09 三題依賴公司文件，須等 C01–C04 定稿後依原文補齊答案與證據定位，補齊並審核後才凍結 hash。保留題檔存放在專案目錄之外，以環境變數 HR_RAG_HOLDOUT_PATH 指定；專案內只保存題數、各類分配與檔案 SHA256，實作 agent 的工作目錄中不得出現保留題內容。驗收報告須揭露公司文件、開發題、保留題各由誰撰寫。保留題的逐題結果先由使用者檢視；實作端看到逐題內容即視為曝光。看過保留答案後若做針對性修改，原保留題改為回歸集並補一套同分布 10 題。沒有人工標準答案就不能進入驗收。

### 9. 後續實作邊界

實作時一次處理 tasks.md 一個階段；先讀對應 spec 和 design；階段2適用第7節核准的保留題延後例外，其他前置驗收不變。超出 10 主文件、增加工具呼叫、改角色矩陣、接真實個資或改門檻，先更新提案／規格／設計／任務，再實作。不得只在聊天裡改要求。OpenSpec 格式驗證不是程式驗收。

### 10. 追溯、回饋及本機告警

一般事件日誌僅含 trace_id、去識別身分、角色、版本、ID、耗時、錯誤碼與成本欄位；完整問題、模型請求（有序提示及最終上下文）、原始輸出、最終答案、主張引用對照與驗證狀態存入本機開發者可讀的受限稽核儲存。請求只保存模型輸入資料，不保存帶憑證的 HTTP headers 或 API 金鑰；模型設定、詞表及組裝預算也入快照。OpenAI 呼叫另存 response id、實際模型 ID、usage（含推理 tokens）與成本估算，供核對與追溯。使用不可變內容及 hash 確保來源更新後仍能重建當次輸入；重播是檢視已保存交換，不再次呼叫模型。預設保留30天，以明確的本機清除命令連同無其他保留引用的稽核快照清除；一般使用者端無重播入口。稽核寫入失敗回傳受控錯誤，不展示沒有追溯證據的成功答案。

使用者對本人 trace_id 提交有用／無用及原因 enum，不新增自由文字個資欄位；本機維護者記錄處理人、狀態、原因、修正參照與回歸結果。以既有開發案例或隔離工程fixture驗證修正，不改固定30題的分布、不將回饋當知識文件。至少展示一次回報→分析→修正→回歸通過的閉環；另測無回歸證據不能標記已修正。維護者以本機CLI操作，沒有新增第四個Demo角色。

## Risks / Trade-offs

- 小型題庫容易過度調整 → 先凍結題目及拆分保留集，報告題數與限制。
- 法規頁與 FAQ 更新不同步 → 以快照與日期證據核對；明顯衝突退回人工，不憑頁面更新日判定優先。
- 法規整份匯入可能稀釋主題 → 保留原文，索引白名單章節，測試條件完整性。
- 本機 1.5B 生成在真實長度上下文正確 0/5、出現簡體與標錯引用 → 2026-10-18 使用者決定生成改用 OpenAI API；0.8 重新實測，不預先承諾延遲。
- 資料離開本機 → 只送問題與已授權的最終上下文，不送身分資訊；不處理真實個資；README 揭露資料流向與 OpenAI 政策連結。
- API 費用失控 → 每次呼叫記錄 usage 與成本，HR_RAG_COST_LIMIT_USD 累計上限，使用者另設後台用量上限；預設測試不連網。
- 限流、服務中斷或模型下架 → 有限次重試後受控失敗並計入錯誤率；鎖定帶日期的模型快照 ID，換模型須重跑 0.8、4.9 與階段 5。
- 外部模型輸出不保證可重現 → 模型支援時 temperature=0，記錄不支援的參數；以 18 次穩定性執行檢查語義一致，不宣稱逐字相同。
- 子片段或查詢超過 encoder 512 tokens 會在匯入或重排時失敗 → 子片段 400、查詢 96 encoder tokens 上限，以實際 tokenizer 檢核。
- 本機只剩兩個 encoder（第一次實測常駐 RSS 約 1 GiB），重排 20 個候選約 6–9 秒 → 0.8 重新量測完整鏈路，0.9 定案常駐策略。
- 保留題若由實作端撰寫或可讀取，就不是未見驗收 → 由不參與調參者草擬、使用者審核定稿，存放專案外，專案內只留 hash；報告照實揭露草擬者。
- 授權文件被模型記住／混入上下文 → 不做多輪與共享答案快取，側路端點再驗權。
- 四份公司文件是虛構 → 所有頁面與引用標示，作品集不聲稱已接入真實企業。
- 原始碼參考來源可能有授權要求 → 若後續採用既有程式碼，保留授權與來源，另外記錄自己新增部分。
