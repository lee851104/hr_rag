# Proposal

## Why

建立繁體中文「企業請假與特休知識助理」求職作品集，以可重現的證據展示官方法規引用、公司流程查詢、檢索前權限控制三項能力。專案從零實作，`../rag-chatbot-main` 僅為參考，不複製為既有實作成果。

## What Changes

2026-10-18 使用者核准依賴調整：1.1、1.2、1.3、1.6與20開發題人工核對通過後，可先執行不讀取保留題的階段2；1.4／1.5保留題格式驗證、合格摘要及SHA256凍結延後至階段4開始前完成。階段1整體仍不可提前標記通過，階段2片段人工核對與其他階段門檻不變。

- 使用 6 份官方主文件與 4 份虛構公司主文件；公司辦法另保留 1 份歷史版本，共 10 個 document_id、11 個初始版本檔案。
- 支援員工、主管、HR 三種角色；由伺服器驗證身分並套用文件權限。
- 分別保存發布／修正日、生效日、失效日、擷取時間；依查詢日期選取有效證據。
- 建立繁體中文語意檢索基線，再比較 BM25 混合檢索及重排序；所有路徑共用權限與時間限制。
- 回答區分官方依據與模擬公司規定，提供可追溯引用；缺乏證據或來源衝突時明確說明。
- 建立 30 題人工評估集、可追蹤日誌及簡單網頁展示；以階段門檻約束後續實作。
- 補齊中文同義詞前處理與上下文去重、排序、長度預算；比較檢索完整性與精確度，驗證固定問題重問三次的語義穩定性。
- 2026-10-18依使用者要求只用開發題改善精確度，不改人工標註或門檻；上下文可啟用保守的明確假別範圍篩選。一般規則、否定、多假別及法規交互引用不據此排除，仍須通過原完整證據與精確度門檻。
- 保存受保護的問題、實際模型上下文、輸出與引用對照；增加文件維護責任、增量索引、使用者回饋與本機異常告警。
- 上述補強均使用既有 10 份主文件；測試 fixture、詞彙表、稽核及回饋不是新增知識文件，不進入知識索引。
- 2026-10-18 規劃審查補正：子片段與查詢受 encoder 512 tokens 上限約束、上下文相關度篩選、評估題逐角色預期、保留題由不參與調參者草擬、使用者審核並存於專案外、民國日期與問答日期規則、生成模型備案順序。
- 2026-10-18 本機 Qwen2.5-1.5B 真實長度實測正確 0/5，使用者決定生成改用 OpenAI API；embedding 與重排留在本機，只把問題與已授權的最終上下文送到 OpenAI，並加上金鑰保護、成本上限與用量紀錄。
- 本次交付規格與任務，不宣稱資料已收集、題目已完成或系統已實作。

### Scope boundaries

2026-10-18選型補充：0.8兩模型皆通過，使用者收到成本比較後指示繼續0.9，凍結較低價的GPT-4.1 mini快照與執行預算。必要時較大模型可依使用者授權評估Luna；不自動切換，仍須查證快照／價格／能力及通過同一可行性門檻，累計1美元上限不變。

2026-10-18 設定補充（使用者要求）：自動讀取專案根目錄不入版控的 `.env`，僅補足 `OPENAI_API_KEY` 與 `HR_RAG_COST_LIMIT_USD`；環境變數優先，不顯示、記錄或寫回金鑰，不因載入設定而呼叫API。

第一版只查詢制度，不計算真實員工剩餘假數、不核准假單、不接人資系統、不儲存真實人事個資。排除多人租戶、SSO、OCR、任意檔案上傳、網路即時搜尋、Agent 自主工具呼叫、多輪對話記憶及正式雲端部署。禁止把虛構公司規定當成真實企業規定或法律。

## Capabilities

### New Capabilities

- `knowledge-corpus`: 文件來源、結構、日期、版本、維護責任、切片與增量匯入。
- `access-control`: 伺服器身分、角色隔離、檢索與引用授權。
- `evidence-retrieval`: 中文前處理、受限候選集合、基線／混合檢索／重排、日期選擇及上下文組裝。
- `grounded-answering`: 證據式回答、來源標示、拒答與展示介面。
- `evaluation-observability`: 人工評估、保留題、完整性／精確度／穩定性比較、受限追溯、回饋告警與交付證據。

### Modified Capabilities

無；這是獨立新專案，沒有既有正式規格。

## Impact

預計新增 Python 後端、SQLite 文件與稽核資料、局部向量索引、受保護的 HTML 展示頁及測試工具。模型透過介面替換：embedding 與重排在本機執行，生成呼叫 OpenAI API（使用者 2026-10-18 授權）。OpenAI 模型快照 ID 在 0.8 真實長度驗證後由 0.9 鎖定；API 金鑰由使用者自行建立並以環境變數提供，實作端不建立或保存金鑰，累計費用受 HR_RAG_COST_LIMIT_USD 限制。完整開發順序與驗收門檻見 design.md、tasks.md；需求與案例見 specs/。

階段5補記：模型輸入的長引用ID採單次請求短ID傳輸，伺服器先驗證實際送出的短ID白名單再還原原始來源，節省既有512輸出token額度；不增加證據或改變門檻。


第五階段開發修正：複合查詢保留原表示，對「以及」後最多兩個長度至少6字的並列子句補算重排，取各候選最大分；不擴大top20候選或top5。特定流程與表單必須有直接證據，不能用一般流程推測。既有標註不變，新人工判定另存且禁止覆蓋既有鍵。

具名表單安全補充：查詢明示詢問表單名稱／識別時，已授權上下文若沒有直接的表單代碼或具名使用敘述，伺服器回資料不足並移除模型猜測。此為必要條件，不聲稱通過即語意正確；仍須人工支持率與完整覆蓋驗收，不讀題號、角色金標或無權來源。

### 第五階段引用一致性修正（2026-10-19）

OpenAI wire改為逐主張引用，由伺服器計算對外Answer.citations，消除兩份引用清單失配；不放寬未知來源或語意完整性檢查。兩次生成審稿僅作開發診斷，未證明有效，不採用。

### 原文選取候選（2026-10-19，使用者同意先試）

針對摘要漏條件，增加開發實驗：模型選出直接回答問題的完整授權段落，伺服器原樣組成回答及引用，不讓模型改寫。先小測，再視結果重跑開發與穩定驗收；不更改標註、必要答案、權限與門檻。未通過前不宣稱替換正式模式。

原文候選v2：為解析正文對其他文件／版本／條文的參照，只為本次已授權上下文另送document_id、version_id、section_id三欄來源標示；不送角色、user_id、帳號、session、路徑或未入上下文的文件資訊。三欄一併計入evidence_budget及完整payload預算。摘要模式仍維持id與正文。允許明確被所問規則準用的其他規定，但不得將不同假別的規則直接混用。

原文候選v2的參照補充由程式執行：模型選段後，只在同一已授權上下文中，補上明示參照文件及具名假別規定的現有完整段落；來源去重、有限閉包、不查上下文外文件。補入段落標記「參照補充」，引用仍經原白名單及當前權限檢核。否定參照不展開，文件代號邊界精確匹配；僅作保守字面依賴補充，不宣稱能完整解析所有法律準用關係。未降低語意／引用支持／完整性驗收。


原文候選v3補充：來源標示以source=[document_id, version_id, section_id]及緊湊JSON傳送，全部計入原2048證據／4096上下文預算，不提高限制。每次請求schema的source_ids採實際送出引用別名的enum，避免文件代號被當成引用ID；本機仍拒絕重複及未知ID。組裝與請求共用build_verbatim_payload計數。明示參照不得跨逗號或否定詞補入排除來源，新增否定範圍回歸；完整原文不等於語意完整，仍須原5.4／5.5人工門檻。

### 原文候選正式採用（2026-10-19）

使用者完成5.4／5.5人工核對（開發26筆、穩定18筆；穩定性第一次匯出有3筆誤選，經使用者本人於核對頁更正後重新匯出，第一次匯出及其計算保留）。依原門檻：可回答14/14、資料不足3/3、版本3/3、引用支持36/36、關鍵主張覆蓋26/26；穩定18/18、引用37/37。正式回答路徑改採verbatim-reference-closure-v3（gpt-4.1-2025-04-14），設定存config/generation.selected.json並由config/models.lock.json的selected_generation以SHA256鎖定；hr_rag.generation.selected_generator()在設定、提示、schema或verbatim.py實作與驗收時不同即拒絕，不退回摘要模式。OpenAISettings()預設值與openai_generator（mini摘要）保留為歷史鎖定，原檔另存config/history/models.lock.2026-10-18.json。預算4096／2048／512／128、60秒逾時、2次重試與US$1累計上限不變；接線只做離線驗證，未新增API呼叫。D11使用者判定為正確，與Codex初查（漏必要性疑義轉人資）不同，以使用者人工判定為準並揭露差異。

### 階段7保留題入口（2026-10-19）

7.2原寫的 `python -m hr_rag.evaluation --split holdout --mode selected --corpus full` 改由 `python -m hr_rag.holdout` 執行四步：`retrieve`（本機檢索組裝、不呼叫API，產生私人上下文標註頁）、`import-labels --export`（匯入使用者完整標註）、`answer`（每角色執行1次真實API）、`score --review`（依使用者答案核對計算保留及30題門檻）。`evaluate()` 新增 `split="holdout"`，保留題檔須在專案外且SHA256等於 eval/holdout.manifest.json，保留題標註必須明確指向專案外檔案。結果、核對頁與標註只存在保留題同層 `stage7/`；主控台與 reports/stage7-holdout-summary.json 只含數字與題號。每步先核對 eval/final.freeze.json（7.1凍結，含程式、設定、評估資料、合併用開發證據及語料指紋），不符即拒絕執行。門檻與原規格相同，未調降。
